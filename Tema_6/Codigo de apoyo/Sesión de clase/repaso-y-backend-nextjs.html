Módulo 01 — Sesión I

HTTP: el idioma de la web.

HTTP (HyperText Transfer Protocol) es el protocolo que usan los navegadores y las aplicaciones para hablar con los servidores. Cuando abres unir.net, tu navegador manda una petición HTTP y el servidor devuelve una respuesta.

Esa es toda la idea: petición → respuesta. Un cliente pregunta, un servidor contesta.

Una petición HTTP, anatomía

GET /api/v1/cars/1 HTTP/1.1
Host: miweb.com
Accept: application/json
Authorization: Bearer eyJhbGciOi...

// (sin cuerpo en GET)

Tres ingredientes:

  • Línea de inicio → verbo (GET), ruta (/api/v1/cars/1) y versión.
  • Headers → metadatos: quién soy, qué formato acepto, mi token...
  • Cuerpo (opcional) → los datos que envío, normalmente JSON.

Una respuesta HTTP

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60

{
  "id": 1,
  "brand": "Ferrari",
  "model": "F40"
}

¿Y qué es eso de "HTTP/1.1"?

HTTP es el protocolo, pero ha tenido varias versiones a lo largo de los años. La línea de inicio de cada petición termina con la versión que se está usando: GET /cars HTTP/1.1.

Versión Año Lo que aporta
HTTP/1.0 1996 Una conexión = una petición. Lentísimo: cargar una web con 30 imágenes implicaba 30 conexiones nuevas.
HTTP/1.1 1997 El que verás casi siempre escrito. Texto plano sobre TCP. Permite reusar la conexión (keep-alive) para varias peticiones seguidas. Cabeceras de host, cacheo, etc.
HTTP/2 2015 Binario en lugar de texto. Multiplexa varias peticiones en una misma conexión simultáneamente. Compresión de cabeceras. Mucho más rápido.
HTTP/3 2022 Va sobre QUIC (UDP) en lugar de TCP. Resuelve problemas de latencia en redes móviles. Aún se está desplegando.

Para ti como desarrollador, no cambia casi nada. Tu código es idéntico: haces fetch('/api/cars') y el navegador y servidor negocian la versión que ambos soportan. Pero saber que existen ayuda a entender por qué a veces tu API "va más rápida de lo esperado" — el navegador está reusando conexiones gracias a HTTP/2.

El header Content-Type

Es la forma de decirle a la otra parte qué formato tiene el cuerpo que estás mandando o devolviendo. Sin él, el receptor tendría que adivinar. 

Content-Type: application/json
Content-Type: text/html; charset=utf-8
Content-Type: image/png
Content-Type: multipart/form-data; boundary=----abc123

Los más comunes en APIs REST:

  • application/json — el 99% de las peticiones y respuestas de tu API.
  • application/x-www-form-urlencoded — formularios HTML clásicos (name=Juan&age=30).
  • multipart/form-data — formularios con archivos (subir una imagen, por ejemplo).
  • text/plain — texto sin estructura.
⚠ Si no envías Content-Type, el servidor no sabe qué hacer

Cuando haces fetch('/api/cars', { method: 'POST', body: JSON.stringify(data) }) tienes que añadir headers: { 'Content-Type': 'application/json' }. Si no, el server intentará parsear como form-encoded y fallará.

En la práctica: ¿qué escribes tú y qué hace el navegador / Next.js?

Hasta aquí has visto cómo es una petición HTTP "por dentro". Pero al programar no escribes HTTP a mano: usas funciones como fetch() en el cliente y funciones como NextResponse.json() en el servidor. El protocolo lo genera la herramienta por ti. Vamos a ver exactamente qué tienes que poner y qué se rellena solo.

🟢 LADO CLIENTE — cómo escribir una petición

En el navegador (o en otro Next.js, o donde sea que haya JavaScript), usas fetch(). Es una función nativa, no necesitas instalar nada. Estos cuatro patrones cubren el 95% de lo que vas a hacer:

① GET — leer datos

// Lo más sencillo: una sola línea
const res = await fetch('/api/v1/cars');
const cars = await res.json();

// Con filtros, igual de fácil
const res = await fetch('/api/v1/cars?brand=Audi');
const audis = await res.json();

Lo que escribes tú: el verbo (GET es por defecto, no hace falta indicarlo), la URL.
Lo que pasa automático: el navegador añade Host, User-Agent, Accept, Cookie... TÚ no tocas eso. El .json() al final parsea el cuerpo automáticamente.

② POST / PUT / PATCH — enviar datos

const res = await fetch('/api/v1/cars', {
  method: 'POST',                              // 👈 obligatorio decir el verbo
  headers: { 'Content-Type': 'application/json' }, // 👈 obligatorio si mandas JSON
  body: JSON.stringify({ brand: 'Audi', model: 'R8' }) // 👈 el cuerpo, como STRING
});

const created = await res.json();

Lo que escribes tú: método, Content-Type, y el body (siempre convertido a string con JSON.stringify).
Automático: el navegador calcula y añade Content-Length, mete las cookies del dominio, gestiona la conexión TCP/TLS...

③ DELETE — borrar

await fetch(`/api/v1/cars/${id}`, { method: 'DELETE' });
// Normalmente DELETE devuelve 204 sin cuerpo, así que ni .json()

④ Comprobar errores

const res = await fetch('/api/v1/cars', { method: 'POST', ... });

// ⚠ fetch NO lanza error en respuestas 4xx/5xx. Tienes que comprobarlo tú.
if (!res.ok) {                    // res.ok = true si status entre 200 y 299
  const err = await res.json();
  throw new Error(err.error ?? `HTTP ${res.status}`);
}
const data = await res.json();
⚠ La trampa más común con fetch

fetch solo lanza si la red falla (sin internet, dominio inexistente...). Si el servidor devuelve 404 o 500, fetch resuelve normalmente y tú tienes que mirar res.ok o res.status. Olvidar esto es el bug número uno al empezar.

🔵 LADO SERVIDOR — cómo escribir una respuesta (Next.js)

En Next.js, una "respuesta a una petición" se escribe creando un archivo route.js dentro de app/api/. Verás esto más a fondo en el módulo de Route Handlers, pero aquí va el patrón mínimo para que ya te suene: 

// app/api/v1/cars/route.js
import { NextResponse } from 'next/server';

// ─── GET /api/v1/cars ──────────────────────────────────────
export async function GET(request) {
  const cars = await fetchCarsFromDB();

  // .json() = (1) convierte el objeto a string
  //          (2) pone Content-Type: application/json automático
  //          (3) status 200 por defecto
  return NextResponse.json(cars);
}

// ─── POST /api/v1/cars ─────────────────────────────────────
export async function POST(request) {
  // 👇 leer el body que mandó el cliente (lo parsea solo)
  const body = await request.json();

  // 👇 validar (decisión TUYA: qué consideras "válido")
  if (!body.brand || !body.model) {
    return NextResponse.json(
      { error: 'brand y model son obligatorios' },
      { status: 400 }   // 👈 TÚ eliges el código de estado
    );
  }

  const created = await saveCar(body);

  return NextResponse.json(created, { status: 201 });
}

Lo que escribes tú: el nombre de la función (= verbo HTTP), qué lee del request, qué decide hacer, qué devuelve y con qué status.
Automático en Next.js: el routing (que app/api/v1/cars/route.js sea accesible en /api/v1/cars), el parseo del body cuando llamas a request.json(), el Content-Type de la respuesta cuando usas NextResponse.json(), el Content-Length, la negociación HTTP/1.1 o /2 con el navegador...

Tu primer fetch + Route Handler en 60 segundos

El esqueleto mínimo, para que veas que es chupado:

// ╔══════════════════════════════════════════════╗
// ║  SERVIDOR — app/api/v1/hello/route.js        ║
// ╚══════════════════════════════════════════════╝
import { NextResponse } from 'next/server';

export async function GET() {
  return NextResponse.json({ message: '¡Hola desde el servidor!' });
}

export async function POST(request) {
  const { name } = await request.json();
  return NextResponse.json({ greeting: `Hola, ${name}` }, { status: 201 });
}
// ╔══════════════════════════════════════════════╗
// ║  CLIENTE — app/page.js (Client Component)    ║
// ╚══════════════════════════════════════════════╝
'use client';

export default function Home() {
  async function handleClick() {
    // Leer
    const r1 = await fetch('/api/v1/hello');
    const hello = await r1.json();
    console.log(hello);  // → { message: '¡Hola desde el servidor!' }

    // Enviar
    const r2 = await fetch('/api/v1/hello', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ name: 'Ana' }),
    });
    const greeting = await r2.json();
    console.log(greeting);  // → { greeting: 'Hola, Ana' }
  }

  return <button onClick={handleClick}>Probar</button>;
}

Esto es todo lo que necesitas saber para empezar a hacer peticiones y respuestas en una aplicación Next.js. El resto del curso son matices: cómo elegir bien la URL, qué status code devolver, cuándo cachear, cómo identificar al usuario. Pero el patrón básico siempre es el mismo: el cliente llama a fetch, el servidor exporta una función con el nombre del verbo.

Cuando hagas tus primeras peticiones, sí o sí tendrás que escribir:

  • En el cliente, en cada fetch que no sea GET: method, headers: { 'Content-Type': 'application/json' }, y body: JSON.stringify(...). Sin esos tres, el servidor no entiende lo que mandas.
  • Después del fetch: comprobar res.ok antes de usar la respuesta. fetch no lanza con errores HTTP.
  • En el servidor: exportar funciones con el nombre del verbo en mayúsculas (GET, POST...) desde un route.js dentro de app/api/. Si lo llamas get o handleGet, no funciona.
  • En el servidor: devolver NextResponse.json(data, { status: N }). El status por defecto es 200; ponlo a 201 en POST con éxito, 400 en validación fallida, 404 si no existe, etc.
  • Si la ruta tiene parámetro dinámico (como app/api/cars/[id]/route.js): la función recibe un segundo argumento { params } de donde sacas el id con const { id } = await params.
Módulo 02

Los verbos HTTP.

Cada petición lleva un verbo (también llamado método) que dice qué quieres hacer. Hay cinco que importan, y cada uno tiene dos propiedades clave:

Seguro

No modifica el estado del servidor. Solo lee.

Idempotente

Si lo llamas N veces, el resultado final es el mismo que si lo llamases una.

Verbo Para qué Seguro Idempotente
GETLeer recursos✓✓
POSTCrear un recurso nuevo✗✗
PUTReemplazar un recurso entero✗✓
PATCHModificar parte de un recurso✗✗
DELETEBorrar un recurso✗✓
Truco para entender idempotencia

Pulsa el botón del ascensor. Da igual que lo pulses 1 vez o 50: el ascensor solo viene una. Eso es idempotente. Pulsar "comprar" en una tienda no es idempotente: si lo pulsas 50 veces te pueden cobrar 50 pedidos.

¿Por qué cada verbo es (o no) idempotente?

La idempotencia no es una decisión arbitraria: depende de qué efecto tiene el verbo sobre el recurso.

GET — idempotente ✓ (y además seguro)

Solo lee. Nunca modifica nada. Llamar 1 vez o 100 deja el servidor exactamente igual. Por eso los navegadores y proxies cachean GET tranquilamente.

POST — NO idempotente ✗

Crea un recurso nuevo cada vez. Llama dos veces a POST /api/v1/orders y tendrás dos pedidos, no uno. Por eso los navegadores muestran el aviso "¿Reenviar formulario?" al refrescar tras un POST: están protegiéndote de duplicar el efecto.

PUT — idempotente ✓

PUT reemplaza el recurso entero con lo que envías. La clave es esa: tú dices cómo debe quedar, no qué cambiar.

// Llamada 1
PUT /api/v1/cars/1
{ "brand": "Audi", "model": "R8", "year": 2024 }
// Resultado: el coche 1 es { Audi, R8, 2024 }

// Llamada 2 (misma petición)
PUT /api/v1/cars/1
{ "brand": "Audi", "model": "R8", "year": 2024 }
// Resultado: el coche 1 es { Audi, R8, 2024 }   ← idéntico

Como describes el estado final, repetir la llamada deja el servidor en ese mismo estado.

PATCH — NO idempotente ✗ (en general)

PATCH es el verbo que más confunde con la idempotencia. La clave es entender que PATCH puede recibir dos tipos de instrucciones radicalmente distintas:

Forma 1 — "Pon estos valores" (absoluta)

PATCH /api/v1/products/1
{ "price": 105 }

Significa: "el campo price debe quedar a 105". Da igual cuánto valiera antes.

  • Llamada 1: precio era 100 → queda en 105
  • Llamada 2: precio era 105 → queda en 105
  • Llamada 3: precio era 105 → queda en 105

El estado final es siempre el mismo. Esto es idempotente.

Forma 2 — "Aplica esta operación" (relativa)

PATCH /api/v1/products/1
[{ "op": "add", "path": "/price", "value": 5 }]

Significa: "súmale 5 al price actual". Depende de cuánto valga ahora.

  • Llamada 1: precio era 100 → queda en 105
  • Llamada 2: precio era 105 → queda en 110
  • Llamada 3: precio era 110 → queda en 115

Cada llamada cambia el resultado. Esto NO es idempotente.

Entonces, ¿por qué la spec dice que PATCH "no es idempotente"?

La especificación HTTP define las propiedades de cada verbo basándose en lo que puede pasar según el estándar, no en lo que tu API en concreto haga:

  • GET → la spec dice "solo lee". Si tu GET respeta eso, garantizado idempotente.
  • PUT → la spec dice "reemplaza el recurso entero con lo que envías". Si tu PUT respeta eso, garantizado idempotente.
  • PATCH → la spec dice "aplica un cambio parcial", sin especificar qué tipo. Como el cambio puede ser relativo (forma 2), la spec marca PATCH como no idempotente en general.

Que tu PATCH concreto sea de la forma 1 (y por tanto, en la práctica, idempotente) no cambia la regla general. La spec habla del verbo, no de tu implementación.

¿Y por qué importa en la vida real?

Imagina que tu app móvil hace un PATCH y la conexión se cae antes de recibir respuesta. ¿Reintentas?

  • Si tu PATCH es forma 1 (absoluta): puedes reintentar tranquilo. Si la primera llamada llegó, la segunda deja todo igual. Si no llegó, la segunda lo arregla.
  • Si tu PATCH es forma 2 (relativa): si reintentas, puedes acabar sumando 5 dos veces. Bug.

Pero el cliente que consume tu API no sabe cuál de las dos formas implementaste. Solo ve el verbo PATCH. Y como la spec dice "no idempotente", el cliente prudente asume lo peor y no reintenta automáticamente.

La regla práctica

Si tu PATCH... Es idempotente en la práctica Pero el cliente lo trata como
Solo hace merge de campos absolutos Sí No idempotente (por seguridad)
Aplica operaciones relativas (sumar, append a lista) No No idempotente

Es decir: aunque tú lo construyas idempotente, el contrato HTTP dice que no lo es, y los clientes actuarán en consecuencia.

DELETE — idempotente ✓

"Borra el recurso 1." Si llamas 1 vez, queda borrado. Si llamas 100, sigue borrado. El estado final es el mismo: el recurso no existe. La segunda llamada devolverá 404, pero eso es información sobre la respuesta, no sobre el efecto en el servidor.

¿Por qué importa esto en la vida real?

Si una petición falla por timeout, ¿la puedes reintentar? Si es idempotente, sí: en el peor caso ya se había ejecutado y reintentar no cambia nada. Si no es idempotente (POST), reintentar puede duplicar el efecto.

Por eso en sistemas serios verás idempotency keys en POSTs (Stripe, por ejemplo): un header Idempotency-Key que el servidor recuerda para detectar reintentos.

"Seguro" e "idempotente" son propiedades contractuales de la especificación HTTP, no comportamientos automáticos. Tu código tiene que cumplirlas. Si haces un GET que registra una visita en la BD, has roto el contrato: GET ya no es seguro, y los caches/proxies asumirán cosas que no son ciertas.

⚠ El error más común en APIs novatas

Devolver 200 OK con un body {"error":"no encontrado"}. ¡Mal! El código de estado es parte de la respuesta. Si fue un fallo, di que fue un fallo: 404, 400 o lo que toque. Tus clientes (y los caches, y los proxies, y tu monitorización) te lo agradecerán.

Módulo 03b

La caché y el header Cache-Control.

Cachear es guardar una copia de algo para reutilizarla y evitar el coste de calcularla o pedirla otra vez. Es uno de los conceptos que más impacto tiene en el rendimiento real de tu aplicación, y a la vez uno de los menos comprendidos al empezar.

¿Dónde vive la caché?

Una petición de tu navegador a tu API puede pasar por varias capas de caché antes de llegar a tu código. Si en alguna de esas capas hay una copia válida, la petición se contesta ahí mismo y tu servidor nunca se entera.

Tres capas, ordenadas de la más rápida a la más lenta:

Navegador

Guarda imágenes, CSS, JS y respuestas HTTP marcadas como cacheables. Puede servirlas sin tocar la red.

CDN / Edge

Servidores en distintas ciudades cachean tu contenido cerca del usuario. Cloudflare, Vercel Edge, AWS CloudFront...

Servidor

Tu propio backend cachea consultas a BD en Redis o memoria, para no calcular lo mismo dos veces.

Una petición bien cacheada puede ser respondida sin que nunca llegue a tu código. El navegador la sirve de su caché. Si no, el CDN. Si no, tu servidor desde Redis. Y solo si no hay nada, calcula la respuesta. Eso es un sistema bien cacheado.

El header Cache-Control

Cache-Control es la forma estándar en HTTP de decir cómo se puede cachear una respuesta. Lo envía el servidor en la respuesta, y todas las capas de caché (navegador, CDN, proxies) lo respetan. 

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=3600

{ "countries": [...] }

Las directivas que más vas a usar:

max-age=N "Cachéame durante N segundos." Tras ese tiempo, la copia se considera caducada.
public "Cualquiera puede cachearme" — incluyendo CDNs y proxies compartidos. Para datos no personales.
private "Solo el navegador del usuario me puede cachear" — los CDNs no. Para datos personales.
no-cache Engañoso: no significa "no cachees". Significa "guarda copia, pero pregúntame antes de usarla cada vez". Útil con ETag.
no-store Esto sí significa "no guardes copia". Para datos sensibles (datos bancarios, datos médicos...).

¿Quién, cuándo y cómo se configura?

Esta es la pregunta clave. Y la respuesta corta: el servidor lo configura, en la respuesta, con un header. Pero hay matices importantes según con qué herramienta trabajes.

QUIÉN: el servidor (siempre)

Cache-Control siempre lo decide y envía el servidor. El cliente puede pedir cosas (con headers como Cache-Control: no-cache en la petición o pulsando "recargar sin caché"), pero la política la marca el servidor en su respuesta.

CUÁNDO: en cada respuesta HTTP

El header viaja en cada respuesta. Tu servidor decide en función de qué endpoint sea:

Datos casi estáticos

Lista de países, tipos de combustible, configuración pública.

public, max-age=86400
Datos personales

Tu perfil, tus pedidos, tu carrito.

private, max-age=0, must-revalidate
Mutaciones

POST, PUT, PATCH, DELETE.

no-store (o ni se cachean por defecto)
Datos sensibles

Saldo bancario, historial médico.

no-store

CÓMO: en Next.js, tres niveles

Next.js te da tres formas de configurar la caché, según dónde estés trabajando:

1 · A nivel de Route Handler (lo más explícito) — escribes el header tú mismo:

// app/api/v1/countries/route.js
import { NextResponse } from 'next/server';

export async function GET() {
  const countries = await getCountries();

  return NextResponse.json(countries, {
    headers: {
      'Cache-Control': 'public, max-age=3600, s-maxage=86400',
      // max-age   = navegador (1h)
      // s-maxage  = CDN (24h)
    },
  });
}

2 · A nivel de página / Server Component — con fetch y opciones de Next:

// app/products/page.js
export default async function ProductsPage() {
  // El propio fetch acepta opciones que Next.js usa para cachear
  const res = await fetch('https://api.tienda.com/products', {
    next: { revalidate: 3600 }  // regenerar cada hora
  });
  const products = await res.json();
  return <ProductList items={products} />;
}

3 · A nivel de configuración del segmento — exportando constantes:

// app/products/page.js
export const revalidate = 3600;             // regenera cada 1h
export const dynamic = 'force-static';       // fuerza estático
// otras opciones: 'force-dynamic', 'auto', 'error'
El truco mental

Si te preguntas "¿esto se cachea?", recuerda: los GET sí, todo lo demás no. Y dentro de los GET, decides tú con qué política. Por defecto Next.js intenta cachear agresivamente lo que pueda — si no quieres eso, marca el endpoint como dinámico.

Cache-Control trabaja junto con ETag y Last-Modified: cuando expira el max-age, el navegador puede revalidar enviando If-None-Match: "etag-xyz"; si el servidor ve que el contenido no ha cambiado responde 304 Not Modified sin cuerpo. Ahorras transferencia pero no la ida y vuelta.

s-maxage es como max-age pero solo aplica a "shared caches" (CDNs). Te permite cachear más tiempo en el CDN que en el navegador del usuario. Vercel y Cloudflare lo respetan.

El refrán de la caché

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton.

Traducido: cachear es fácil. Saber cuándo invalidar la caché (porque los datos han cambiado) es el problema difícil. Si tu UI muestra datos de hace 10 minutos cuando el usuario espera datos al segundo, eso es un bug de invalidación.

En tu proyecto Next.js, sí o sí, vas a configurar:

  • La política de caché de cada Route Handler de tipo GET. Decisión obligatoria endpoint a endpoint: public, max-age=N para datos compartidos, private para datos del usuario, no-store para sensibles. Si no lo haces, Next.js elige por ti — y casi siempre elige mal para tu caso.
  • El comportamiento de fetch en Server Components que llamen a APIs externas. Por defecto Next.js cachea agresivamente. Si los datos cambian, añade { next: { revalidate: N } } o { cache: 'no-store' }.
  • Los export const de cada página que tenga datos dinámicos: export const revalidate = 60 o export const dynamic = 'force-dynamic' según convenga.
  • Nunca, jamás, cachear respuestas con datos personales como public. Si el endpoint devuelve algo que depende del usuario logueado, usa private (y la respuesta solo vivirá en el navegador de ese usuario, nunca en el CDN).
Módulo 04

REST: el estilo arquitectónico.

REST (REpresentational State Transfer) lo definió Roy Fielding, uno de los padres del propio HTTP. No es un protocolo ni una librería: es un estilo, un conjunto de reglas para diseñar APIs sobre HTTP de forma predecible.

Antes de seguir: API, API REST y RESTful

Tres palabras que se usan a menudo como si fueran lo mismo. No lo son.

¿Qué es una API?

API = Application Programming Interface. Una API es el contrato que un programa expone para que otros programas hablen con él. Igual que un mando a distancia es la "interfaz" entre tú y la tele (no necesitas saber cómo funciona la tele por dentro: solo qué botones hay y qué hace cada uno), una API es la lista de "botones" que un programa ofrece a otros programas.

Cuando hablamos de APIs en la web, normalmente nos referimos a APIs HTTP: un servidor expone unas URLs concretas, tú haces peticiones HTTP a esas URLs y recibes datos (normalmente JSON). Pero ojo, el concepto es más amplio: la fetch() del navegador también es una API, los métodos de un objeto en JS también... cualquier "puerta de entrada" definida es una API.

¿Qué es una API REST?

Una API REST es una API HTTP diseñada siguiendo el estilo REST. Es decir, una API que:

  • Expone recursos (sustantivos) accesibles por URL: /users, /orders...
  • Usa los verbos HTTP con su semántica estándar (GET lee, POST crea, etc.).
  • Es stateless: cada petición es autosuficiente.
  • Usa los códigos de estado HTTP correctamente.
  • Suele intercambiar datos en JSON.

La idea clave: cualquier desarrollador, viendo solo POST /api/v1/orders, ya intuye qué hace. Esa predictibilidad es el valor de REST.

¿Qué significa RESTful?

"RESTful" es el adjetivo. Una API es RESTful cuando cumple todas las reglas del estilo REST de forma rigurosa. En la práctica, casi nadie es 100% RESTful: hay APIs que se llaman REST pero hacen concesiones (POST con verbos en la URL, login en /login en lugar de /tokens, etc.).

Un símil útil: "vegetariano" describe un estilo de alimentación; "vegetal" es el adjetivo. Una persona que come 90% verduras y de vez en cuando carne es "casi vegetariana". Las APIs "casi REST" son la norma, no la excepción.

Resumen rápido

API = el contrato entre programas (concepto general).
API REST = una API HTTP diseñada con el estilo REST.
RESTful = el adjetivo que se aplica a una API REST que cumple todas las reglas.

Los tres pilares de REST

  • Recursos, no acciones. Tu API expone cosas (cars, users, rooms), no verbos. La acción la pone el método HTTP.
  • Stateless. Cada petición es independiente. El servidor no recuerda nada de la anterior.
  • Verbos estándar. GET/POST/PUT/PATCH/DELETE con la semántica que ya viste.

«No hay estado»: ¿qué significa eso?

Imagina que pides GET /api/profile. El servidor no recuerda que hace 2 segundos hiciste POST /api/login. ¿Cómo sabe entonces quién eres?

Respuesta: tú se lo dices en cada petición. Normalmente con un token en el header Authorization: 

GET /api/profile
Authorization: Bearer eyJhbGciOi...
Ventaja servidor
Escala

No guarda sesiones. Cualquier instancia puede atender cualquier petición.

"Coste" cliente
Recordar

El cliente debe almacenar y mandar el token cada vez.

"Stateless" no significa "sin sesión": significa sin estado en el servidor entre peticiones. Las cookies de sesión clásicas violan REST (el server guarda el sessionId → user). Por eso JWT y los Bearer tokens encajan tan bien con REST: el estado vive dentro del token, firmado, y el server lo verifica sin almacenar nada.

Orientación a recursos

Identifica los sustantivos de tu dominio. Esos son los recursos. Y se nombran en plural:

✓/cars, /users, /restaurants, /roomsSustantivos en plural. Una colección.
✗/getCar, /createUser, /listRoomsEl verbo lo da el método HTTP, no la URL.
✗/car, /user (singular)Inconsistente: GET /car ¿lista coches? ¿uno solo? El plural lo aclara.
Módulo 04b

Identificar al usuario: cookies, Bearer y JWT.

Acabamos de ver que REST es stateless: el servidor no recuerda nada entre peticiones. Entonces, ¿cómo sabe el servidor quién está pidiendo? El cliente tiene que contárselo en cada petición. Hay dos mecanismos estándar.

Mecanismo 1 · Bearer tokens

El cliente manda un token en el header Authorization: 

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIi...

"Bearer" significa "al portador" — quien lleve este token, tiene acceso. Como un billete de tren al portador: no comprueba quién eres, solo que tienes el papelito. Por eso hay que protegerlos: si alguien roba tu Bearer token, puede hacerse pasar por ti.

¿Qué es un JWT?

JWT (JSON Web Token, se pronuncia "jot") es el formato de token más común. Un JWT es una cadena en tres partes separadas por puntos:

  • Header (Base64): qué algoritmo de firma se usa, p.ej. {"alg":"HS256"}.
  • Payload (Base64): los datos que el server quiere recordar, p.ej. {"sub":"user_123","exp":1705000000}. ¡Visible, no es cifrado!
  • Firma: HMAC(secret, header + "." + payload). Solo el server con la clave secreta puede generarla.

La gracia: el servidor no necesita guardar nada. Cuando recibe el JWT, recalcula la firma con su clave secreta y la compara. Si coincide, el token es válido. Si alguien manipula el payload, la firma deja de coincidir y el token se rechaza.

☢ Lo que NUNCA debes hacer con JWT
  • Meter datos sensibles en el payload (contraseñas, números de tarjeta...). Recuerda: el payload es legible por cualquiera.
  • Guardar JWTs en localStorage: vulnerables a XSS. Usa cookies con HttpOnly y Secure.
  • Aceptar alg: none sin firma. Hay vulnerabilidades históricas con esto.
  • Usar JWT con expiración larga sin un mecanismo de invalidación: si filtras un JWT, no puedes "borrarlo" del servidor.

Mecanismo 2 · Cookies

Una cookie es un trocito de información que el servidor le pide al navegador que guarde, y que el navegador reenvía automáticamente en cada petición a ese dominio. Esa es la diferencia clave con Bearer: las cookies se mandan solas, no las añade tu código.

El flujo clásico:

// 1. Login: el cliente manda credenciales
POST /api/login
Content-Type: application/json

{ "email": "a@b.com", "password": "..." }

// 2. El servidor responde y le PIDE al navegador que guarde una cookie
HTTP/1.1 200 OK
Set-Cookie: session=abc123xyz; HttpOnly; Secure; SameSite=Lax; Max-Age=86400

// 3. A partir de ahora, el navegador la manda en CADA petición — solo
GET /api/profile
Cookie: session=abc123xyz

¿Quién, cuándo y cómo se configuran las cookies?

QUIÉN: el servidor

El servidor es quien crea la cookie con un header Set-Cookie en la respuesta. El navegador la guarda y la devuelve sola en peticiones futuras al mismo dominio. JavaScript del cliente también puede crear cookies (document.cookie = "...") pero esto es mala práctica para autenticación: las cookies de sesión las debe crear siempre el servidor con HttpOnly.

CUÁNDO: en la respuesta del login (y al expirar)

La cookie se setea en la respuesta del POST /api/login (o equivalente). Permanece en el navegador hasta que expire (Max-Age) o hasta que el servidor la borre con un Set-Cookie nuevo y vacío. En logout, el servidor la borra explícitamente.

CÓMO: en Next.js, con la API cookies()

Next.js da una API helper cookies() de next/headers que envuelve la lectura/escritura de cookies en Server Components y Route Handlers:

// app/api/v1/login/route.js (en realidad sería /api/v1/sessions, pero...)
import { cookies } from 'next/headers';
import { NextResponse } from 'next/server';

export async function POST(request) {
  const { email, password } = await request.json();
  const user = await authenticate(email, password);

  if (!user) {
    return NextResponse.json({ error: 'invalid' }, { status: 401 });
  }

  // Generamos un JWT firmado con los datos mínimos del usuario
  const token = await signJWT({ sub: user.id, role: user.role });

  // Y lo guardamos DENTRO de una cookie HttpOnly: lo mejor de los dos mundos
  const cookieStore = await cookies();
  cookieStore.set('session', token, {
    httpOnly: true,    // JS del cliente NO puede leerla → protege de XSS
    secure: true,      // solo viaja por HTTPS
    sameSite: 'lax',    // protege de CSRF
    maxAge: 60 * 60 * 24, // 24 horas
    path: '/',
  });

  return NextResponse.json({ user });
}

Y para leerla más adelante (en otra ruta, o en un Server Component):

import { cookies } from 'next/headers';

export async function GET() {
  const cookieStore = await cookies();
  const token = cookieStore.get('session')?.value;
  if (!token) return NextResponse.json({ error: 'no auth' }, { status: 401 });

  const payload = await verifyJWT(token); // lanza si está mal firmado
  return NextResponse.json({ userId: payload.sub });
}

Atributos importantes de una cookie

HttpOnly JavaScript del navegador no puede leerla. Crítico contra XSS. Para cookies de sesión, siempre.
Secure Solo viaja por HTTPS. En producción, siempre.
SameSite Controla si la cookie viaja en peticiones de otros dominios. Lax es el default razonable; Strict es máximo aislamiento; None permite cross-site (requiere Secure). Protege contra CSRF.
Max-Age Cuántos segundos vive la cookie. Sin este atributo, es de "sesión" (se borra al cerrar el navegador).
Path En qué rutas del dominio se envía la cookie. Normalmente /.

Cookie de sesión vs Bearer token — ¿cuándo usar cada uno?

Cookie Bearer / JWT en header
Envío Automático por el navegador Manual: tú añades el header
Almacén Cookie del navegador (HttpOnly) Memoria, localStorage, cookie...
Apps no-web Difícil (cliente móvil, CLI...) Fácil — es solo un header
CSRF Vulnerable (necesita SameSite + tokens) Inmune (no se envía solo)
XSS Más seguro (HttpOnly) Vulnerable si está en localStorage

En la práctica, para webs Next.js que sirven a navegadores: la tendencia moderna es cookies HttpOnly con un JWT dentro. Combinas lo mejor de ambos: el JWT te da statelessness y firma criptográfica; la cookie HttpOnly te da el envío automático y la protección contra XSS. Es exactamente el ejemplo de código que viste arriba.

Para APIs públicas que sirven a apps móviles o terceros: Bearer tokens en el header Authorization. Las cookies no funcionan bien fuera del navegador.

"Cookie de sesión" tradicionalmente significaba: el server guarda { session_id → user_id } en memoria/Redis y la cookie solo lleva el session_id opaco. Esto viola el principio stateless de REST porque el server tiene que recordar la sesión.

La versión moderna mete un JWT firmado dentro de la cookie HttpOnly. El server no guarda nada: verifica la firma del JWT en cada petición. Sigue siendo stateless ✓.

Caché vs cookies: dos cosas distintas que se confunden

Llegamos a una pregunta legítima: "si las cookies y la caché se setean con un header en la respuesta, ¿son lo mismo?". No. Son conceptos opuestos:

Para qué sirven Caché: ahorrar trabajo. Reutilizar respuestas viejas en lugar de recalcular. Cookies: identificar al usuario. Mandar contexto al servidor.
Quién las setea El servidor, en cada respuesta cacheable. El servidor, normalmente al hacer login.
Quién las usa El navegador, los CDNs, los proxies — para no volver a pedir lo mismo. El servidor — para saber quién está pidiendo.
Dirección Servidor → cliente (con instrucciones de cómo guardar). Servidor ↔ cliente (ida y vuelta en cada petición).
Vida Hasta que expire max-age o se invalide. Hasta que expire Max-Age o el server la borre.
Header Cache-Control Set-Cookie / Cookie
⚠ Y se pelean entre sí

Si tu respuesta lleva una cookie de sesión y es cacheada por un CDN, la cookie del usuario A puede acabar en la respuesta cacheada que sirves al usuario B. Catástrofe de seguridad.

Por eso las respuestas con datos personales deben llevar Cache-Control: private (o no-store): los CDNs no las cachearán. Solo el navegador del propio usuario puede.

Recapitulando: ¿de qué se ocupa principalmente el desarrollador Next.js?

Si te quedas con una sola idea de este módulo (y del de caché), que sea esta: como dev, tu trabajo es decidir la política, no implementar la maquinaria. La maquinaria (firmar JWT, parsear cookies, respetar Cache-Control) ya está hecha — por el navegador, por Next.js, por la librería de turno. Tu responsabilidad es elegir bien qué política aplicar a cada endpoint.

En tu proyecto Next.js, sí o sí, vas a configurar:

  • Un secret para firmar tus JWT. En .env.local (¡nunca en el repo!) define JWT_SECRET con un valor aleatorio largo (32+ bytes). Sin esto, no puedes firmar ni verificar nada. Es lo primero que se hace.
  • El endpoint de login (típicamente POST /api/v1/sessions): valida credenciales, firma el JWT, lo mete en una cookie con cookieStore.set('session', token, { httpOnly: true, secure: true, sameSite: 'lax', maxAge: ..., path: '/' }).
  • El endpoint de logout: borra la cookie con cookieStore.delete('session').
  • La verificación del token en cada endpoint privado: en el Route Handler (o, mejor aún, en el proxy.js que ya vimos para no repetirlo 50 veces), lee la cookie, verifica el JWT, y si falla devuelve 401.
  • Marcar como private o no-store toda respuesta con datos personales. Si un endpoint devuelve algo que depende del usuario logueado y se cachea como public, un CDN puede servirle los datos de Alice a Bob. Es un fallo de seguridad clásico.
  • El payload mínimo en el JWT. Solo sub (user id), exp (caducidad), y a lo sumo role. Nada sensible — recuerda que es legible.
  • Una expiración razonable: 15 minutos a 24 horas según el caso. JWTs muy largos sin mecanismo de revocación son una pesadilla.

Lo que no tienes que implementar tú: el cifrado HMAC de la firma, el parseo Base64, la lógica del header Set-Cookie, la negociación de HTTP/2, el respeto del Cache-Control. Eso lo hacen las herramientas. Librerías recomendadas: jose (firma/verificación de JWT moderna, edge-ready) o @auth/core (NextAuth/Auth.js si quieres OAuth de terceros).

Módulo 05

Diseño de URLs RESTful.

Aquí es donde la mayoría de APIs novatas la lían. Pero antes de las reglas, dos preguntas que seguro te has hecho ya.

¿Qué es eso del /v1/?

Te habrás fijado en que todas las URLs llevan /api/v1/.... Eso es versionado de la API, y es una convención de oro.

Imagina que llevas seis meses con tu API /api/cars en producción. La usan 5 apps móviles, 2 webs, un servicio interno y un cliente externo. Un día decides cambiar el formato de respuesta: ahora brand se llama manufacturer. ¡Acabas de romper a todos tus clientes a la vez!

El versionado te da una salida elegante:

// La versión vieja sigue funcionando para los clientes que aún no migraron
GET /api/v1/cars  →  { brand: "Audi", ... }

// La versión nueva, con el cambio, vive en paralelo
GET /api/v2/cars  →  { manufacturer: "Audi", ... }

Los clientes migran cuando puedan. Tú deprecas v1 cuando ya nadie la use. Cero rupturas.

¿Cuándo subir versión?

Solo ante cambios incompatibles (breaking changes): renombrar campos, eliminarlos, cambiar tipos, cambiar el formato de errores. Añadir un campo nuevo opcional no rompe nada y se hace en la misma versión.

Hay tres escuelas de versionado:

  • En la URL (/api/v1/cars): la más visible, fácil de probar, fácil de cachear. Es la habitual.
  • En el header Accept: application/vnd.miapi.v1+json: más "puro" REST (la URL identifica el recurso, no la versión), pero molesto para depurar.
  • Por content negotiation: la respuesta cambia según el Accept-Version. Lo ves en GitHub API, por ejemplo.

En la práctica, casi todo el mundo usa la primera por simplicidad.

¿Es "URL" o "URI"?

En el PPT habrás visto la palabra URI. Y aquí estamos usando URL. ¿Cuál es la diferencia?

URI · Uniform Resource Identifier

Cualquier cadena que identifica un recurso. La categoría general. Puede o no decirte cómo acceder a él.

URL · Uniform Resource Locator

Una URI que además te dice cómo localizar el recurso (protocolo + dirección). Es un tipo de URI.

En analogía:

  • URN (otra subfamilia de URIs) sería como tu DNI: urn:isbn:0451450523. Te identifica, pero no te dice dónde encontrarme.
  • URL sería como tu dirección postal: https://miweb.com/cars/1. Te identifica y te dice cómo llegar (por https, en este servidor).

En la práctica, en el contexto de APIs REST sobre HTTP, las palabras URL y URI se usan intercambiablemente porque todas nuestras URIs son URLs (todas empiezan por http:// o https:// y permiten localizar el recurso). Roy Fielding usaba "URI" en su tesis porque es el término más general y formal. Tu mánager probablemente diga "URL". Las dos son válidas en este contexto.

Las tres reglas

Regla 1 — Plural siempre

✗GET /api/v1/car/1
✓GET /api/v1/cars/1

Regla 2 — Path Param ≠ Query Param

Path Param = parte del camino. Identifica un recurso concreto: /cars/1.
Query Param = lo que va después de ?. Sirve para filtrar, ordenar o paginar.

✗GET /api/v1/cars?id=1El ID identifica el recurso → debe ir en path.
✗GET /api/v1/cars/Ferrari"Ferrari" no es un ID, es un atributo → query.
✗GET /api/v1/cars/Brand/FerrariNo metas atributos en el path.
✓GET /api/v1/cars/1Acceso por ID → path param.
✓GET /api/v1/cars?brand=FerrariFiltro por atributo → query param.
✓GET /api/v1/cars?brand=Ferrari&fuelType=gasVarios filtros, sin esfuerzo.

Regla 3 — La semántica la pone el verbo

No metas create, delete, update en la URL. Ya lo dice el método.

✗POST /api/v1/cars/createRedundante: POST es "crear".
✗DELETE /api/v1/cars/1/deleteDELETE ya borra. Sobra.
✗POST /api/v1/login"login" es un verbo. Modela el recurso: una sesión, un token.
✗PATCH /api/v1/cars/1/updateNameEndpoints atados a una operación = pesadilla de mantener.
✗GET /api/v1/cars/search?q=...Filtra con query params en la colección, no inventes endpoints.
✓POST /api/v1/carsCrear sobre la colección.
✓DELETE /api/v1/cars/1
✓POST /api/v1/tokensLogin = "crear un token". Recurso, no verbo.
✓PATCH /api/v1/cars/1El cuerpo dice qué cambiar (Merge Patch / JSON Patch).

Route Handlers en Next.js.

Vale, ya sabes diseñar una API. Ahora a implementarla. En Next.js (App Router) usas Route Handlers: archivos especiales route.js dentro de app/api/ que Next.js entiende como endpoints HTTP.

Estructura de carpetas

app/
├── api/
│   └── cars/
│       ├── route.js        // → /api/cars   (GET listado, POST crear)
│       └── [id]/
│           └── route.js    // → /api/cars/:id  (GET, PUT, PATCH, DELETE)
└── page.js

Cada función exportada se corresponde con un verbo HTTP. ¡Esa es toda la magia!

Ejemplo mínimo: /api/cars/route.js

import { NextResponse } from 'next/server';

// Persistencia simulada (en memoria — desaparece al reiniciar)
const cars = new Map([
  [1, { id: 1, brand: 'Ferrari', model: 'F40' }],
]);

// GET /api/cars  → listar (con filtro opcional ?brand=...)
export async function GET(request) {
  const { searchParams } = new URL(request.url);
  const brand = searchParams.get('brand');

  let list = [...cars.values()];
  if (brand) list = list.filter(c => c.brand === brand);

  return NextResponse.json(list);
}

// POST /api/cars  → crear
export async function POST(request) {
  const body = await request.json();

  if (!body.brand || !body.model) {
    return NextResponse.json(
      { error: 'brand y model son obligatorios' },
      { status: 400 }
    );
  }

  const id = cars.size + 1;
  const car = { id, ...body };
  cars.set(id, car);

  return NextResponse.json(car, { status: 201 });
}

Y para un recurso concreto: /api/cars/[id]/route.js

export async function GET(request, { params }) {
  const { id } = await params;
  const car = cars.get(Number(id));

  if (!car) {
    return NextResponse.json({ error: 'no encontrado' }, { status: 404 });
  }
  return NextResponse.json(car);
}

export async function DELETE(request, { params }) {
  const { id } = await params;
  const existed = cars.delete(Number(id));

  if (!existed) {
    return NextResponse.json({ error: 'no existe' }, { status: 404 });
  }
  return new Response(null, { status: 204 }); // 204 sin cuerpo
}

Módulo 09

Del diagrama al SQL.

Las reglas para pasar un diagrama a tablas son tres, según la cardinalidad:

Regla 1 · Cada entidad → una tabla

Sin sorpresas: si tienes Persona y Coche, tendrás dos tablas.

Regla 2 · 1:N → propagación de clave

La clave del lado "1" se copia (como FK) en la tabla del lado "N". No se crea tabla nueva.

CREATE TABLE personas (
  dni       VARCHAR(9) PRIMARY KEY,
  nombre    VARCHAR(50) NOT NULL,
  apellidos VARCHAR(100) NOT NULL
);

CREATE TABLE coches (
  id     SERIAL PRIMARY KEY,
  modelo VARCHAR(50) NOT NULL,
  dueno  VARCHAR(9) REFERENCES personas(dni)  -- 👈 FK propagada
);

Regla 3 · N:M → tabla intermedia

Necesitas una tercera tabla cuya PK es compuesta por las dos FK.

CREATE TABLE trabajadores (
  id     SERIAL PRIMARY KEY,
  nombre VARCHAR(50)
);

CREATE TABLE tareas (
  id          SERIAL PRIMARY KEY,
  descripcion VARCHAR(200)
);

-- Tabla intermedia: solo existe para conectar las otras dos
CREATE TABLE trabajadores_tareas (
  trabajador_id INT REFERENCES trabajadores(id),
  tarea_id      INT REFERENCES tareas(id),
  PRIMARY KEY (trabajador_id, tarea_id)  -- 👈 PK compuesta
);

Regla 4 · 1:1 → depende

  • (0,1) — (0,1): tabla intermedia (para evitar nulos en cualquiera de los lados).
  • (0,1) — (1,1): la clave del lado obligatorio se propaga al opcional. Sin tabla nueva.
  • (1,1) — (1,1): da igual hacia dónde propagas. Sin tabla nueva.

El tipo SERIAL en PostgreSQL es azúcar para "INT con secuencia auto-incremental". En proyectos modernos verás también GENERATED ALWAYS AS IDENTITY (estándar SQL) y, cada vez más, UUIDs como PK para evitar exponer IDs secuenciales en URLs.

Las FK no son "obligatorias" para que la BD funcione, pero sin ellas pierdes integridad referencial: nada impide tener un coche con dueño 9999999 que no existe. ¡Ponlas siempre!

Lo que tu equipo realmente usa: Docker + PostgreSQL + DataGrip

  • Docker levanta un PostgreSQL en tu máquina sin instalarlo "a mano":
    docker run -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres
  • DataGrip (o DBeaver, pgAdmin…) es el cliente gráfico para mirar tablas, ejecutar consultas y crear esquemas.
  • Neon es PostgreSQL como servicio en la nube — te da una URL y a correr.

⚠ Por qué .env.local

Next.js carga automáticamente .env.local en local y lo ignora en git por defecto. Nunca commitees credenciales: si lo haces, asume que están públicas y rótalas. Hay bots que rastrean GitHub buscando claves.

Paso 3 · Un archivo utilitario _db.js

// app/api/_db.js
import { Pool } from 'pg';

// Un único pool reutilizable. Es CLAVE no crear uno nuevo
// por petición o saturarías la BD.
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
});

export async function query(text, params) {
  return pool.query(text, params);
}

// Para cuando varias escrituras deben ir "todo o nada"
export async function transaction(fn) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (e) {
    await client.query('ROLLBACK');
    throw e;
  } finally {
    client.release();
  }
}
Transacciones, en una frase

Una transacción es un grupo de operaciones de escritura que o se ejecutan todas o no se ejecuta ninguna. Caso clásico: transferir 100€ de A a B. Si restas a A pero falla el sumar a B, sin transacciones se pierden 100€. Con transacciones, si falla algo se hace ROLLBACK y todo vuelve atrás.

Módulo 11 — Sesión III

Proxies: lógica transversal.

Imagina que tienes 50 endpoints y todos necesitan comprobar si el usuario está logueado. ¿Vas a escribir esa comprobación 50 veces? No. Para eso están los proxies (en Next.js antiguo se llamaban middleware).

Un proxy es un punto de interceptación: un código que se ejecuta antes de que la petición llegue a su destino (página, server component o route handler). Puede:

1 · Continuar

Llamar a next(): la petición sigue su curso.

2 · Redirigir

Mandar al cliente a otra URL (la URL cambia en el navegador).

3 · Reescribir

Servir contenido de otra ruta sin cambiar la URL visible.

El archivo proxy.js

// proxy.js (en la raíz del proyecto, junto a app/)
import { NextResponse } from 'next/server';

export function proxy(request) {
  // 1 · Generar un x-request-id para trazabilidad
  const requestId = request.headers.get('x-request-id') ?? crypto.randomUUID();

  // 2 · Comprobar autenticación en rutas privadas
  if (request.nextUrl.pathname.startsWith('/admin')) {
    const token = request.cookies.get('session');
    if (!token) {
      return NextResponse.redirect(new URL('/login', request.url));
    }
  }

  // 3 · Continuar pasando el x-request-id al siguiente eslabón
  const response = NextResponse.next();
  response.headers.set('x-request-id', requestId);
  return response;
}

// Limita las rutas en las que se ejecuta (¡rendimiento!)
export const config = {
  matcher: ['/admin/:path*', '/api/:path*'],
};
⚠ Edge Runtime, no Node.js

El proxy se ejecuta en Edge Runtime (V8 ligero), no en Node.js. Eso significa:

  • NO puedes usar fs, child_process ni la mayoría de módulos de Node.
  • NO puedes usar drivers de BD pesados (como pg).
  • SÍ puedes usar Web APIs: fetch, Request, Response, Headers, URL, crypto, cookies.
  • Debe ser rápido: se ejecuta en cada petición que pase por el matcher.

Hasta Next.js 15 el archivo se llamaba middleware.js y la función middleware(request). Desde Next.js 16, App Router recomienda proxy.js y proxy(request). La semántica es idéntica; el rename clarifica que no es un middleware tipo Express (no se encadena, solo hay uno).

El matcher acepta sintaxis tipo path-to-regexp y se compila a un edge function. Si lo dejas vacío, el proxy se ejecuta en todas las peticiones (incluyendo assets estáticos) — desastre de rendimiento. Siempre define matcher.

Módulo 12

Redirect vs rewrite.

Es la distinción más confusa al empezar. Y la más importante.

REDIRECT

El servidor responde con un 3xx y un nuevo Location. El navegador hace una nueva petición a esa URL.

→ La URL cambia en la barra del navegador.

REWRITE

El servidor sirve el contenido de otra ruta interna. El navegador no se entera.

→ La URL no cambia. Es transparente.

¿Cuándo usar cada uno?

RedirectLogin obligatorio (te mando a /login), URL antigua que ya no existe (SEO con 301), versión nueva del sitio.
RewriteA/B testing (sirvo /landing a unos y /landing-b a otros sin que lo vean), prefijos de idioma (/es/page sirve realmente /page con locale=es), migraciones progresivas.

API, Server Components y Client Components.

Pregunta de oro: "si Next.js tiene Server Components que ya corren en el servidor y pueden ir a la BD directamente, ¿para qué crear una carpeta /api/ y endpoints REST?"

La respuesta es "depende", y entender cuándo usar cada cosa es probablemente la decisión arquitectónica más importante en Next.js moderno.

Recordatorio: Server Component vs Client Component

Server Component (por defecto en App Router)

Se renderiza en el servidor. Puede leer archivos, tocar la BD, leer secretos. NO tiene useState, useEffect, ni puede manejar clicks. El usuario recibe HTML ya renderizado.

Client Component (lleva 'use client' arriba)

Se renderiza en el navegador. Tiene hooks, eventos, estado, todo el React clásico. NO puede tocar la BD ni leer secretos: su código viaja al cliente.

Y entre medias está el tercer espacio: las Route Handlers (app/api/.../route.js), que son endpoints HTTP que viven en el servidor.

Las tres rutas para conseguir datos

Ruta A · Server Component → BD directamente

// app/cars/page.js — es un Server Component (por defecto)
import { query } from '@/lib/db';

export default async function CarsPage() {
  // 👇 Sin fetch. Sin /api. Hablamos directamente con la BD.
  const { rows: cars } = await query('SELECT * FROM cars');

  return (
    <ul>
      {cars.map(c => <li key={c.id}>{c.brand} {c.model}</li>)}
    </ul>
  );
}

✓ Ventajas:

  • Más rápido: no hay HTTP. No hay serialización JSON. No hay red.
  • Más simple: menos código. Menos archivos.
  • Más seguro: la query no viaja al cliente.
  • SEO perfecto: el HTML llega ya con los datos.

✗ Limitaciones:

  • Solo funciona al renderizar la página. Si el usuario hace click en "filtrar", no puedes refrescar sin recargar (a menos que uses Server Actions).
  • Los datos no son accesibles desde otros clientes (apps móviles, integraciones externas...).

Ruta B · Client Component → fetch a /api/...

'use client';
import { useState, useEffect } from 'react';

export default function CarFilter() {
  const [cars, setCars] = useState([]);
  const [brand, setBrand] = useState('');

  useEffect(() => {
    // 👇 Aquí SÍ necesitamos un endpoint HTTP
    fetch(`/api/v1/cars?brand=${brand}`)
      .then(r => r.json())
      .then(setCars);
  }, [brand]);

  return (
    <>
      <input value={brand} onChange={e => setBrand(e.target.value)} />
      <ul>{cars.map(c => <li key={c.id}>{c.brand}</li>)}</ul>
    </>
  );
}

Aquí sí necesitas el endpoint /api/v1/cars. ¿Por qué? Porque el componente vive en el navegador, y el navegador no puede hablar con tu BD. Necesita pedírselo a alguien que sí pueda — y ese alguien es tu Route Handler.

Ruta C · Server Action (atajo moderno)

// app/cars/actions.js
'use server';
import { query } from '@/lib/db';

export async function getCarsByBrand(brand) {
  const { rows } = await query(
    'SELECT * FROM cars WHERE brand = $1', [brand]
  );
  return rows;
}

// app/cars/CarFilter.js
'use client';
import { getCarsByBrand } from './actions';

export default function CarFilter() {
  const [cars, setCars] = useState([]);
  async function handleSearch(brand) {
    // 👇 No hay /api. Llamas a la función como si fuera local.
    // Next.js se encarga del HTTP por debajo.
    const result = await getCarsByBrand(brand);
    setCars(result);
  }
  // ...
}

Las Server Actions son el atajo: escribes una función con 'use server' y la llamas desde un Client Component como si fuera local. Next.js genera por debajo el endpoint HTTP, la serialización, etc. Magia.

Entonces... ¿cuándo crear la carpeta /api/?

SÍ crear /api/ Cuando otros clientes (apps móviles, integraciones externas, webhooks de terceros, otra app distinta) necesiten consumir tus datos. Una API REST con /api/v1/... es el contrato público hacia fuera.
SÍ crear /api/ Cuando necesitas un webhook (Stripe te llama a una URL, GitHub te notifica un push...). Sí o sí necesitas un endpoint HTTP público.
SÍ crear /api/ Cuando quieres separar arquitectónicamente front y back, o estás migrando desde una arquitectura tradicional, o tu equipo está organizado por especialidades.
NO crear /api/ Para datos que solo consume tu propia web al renderizar. Mejor: Server Component que lee la BD directamente. Más rápido, más simple.
NO crear /api/ Para acciones desde Client Components (mutaciones, formularios, filtros). Mejor: Server Actions. Menos boilerplate.

Resumen: árbol de decisión

¿Necesito datos en una página?
└─ ¿Es para mostrar al renderizar?
└─ Server Component → BD directa
└─ ¿Es para una acción del usuario (click, formulario)?
└─ Server Action
└─ ¿Lo va a consumir alguien fuera de mi web?
└─ Route Handler en /api/v1/...
└─ ¿Es un webhook entrante?
└─ Route Handler en /api/webhooks/...
Y entonces, ¿por qué este curso enseña /api/ con tanto detalle?

Porque entender REST y los Route Handlers es fundamento. Los Server Components y las Server Actions son azúcar sintáctico: por debajo, Next.js sigue hablando HTTP. Si no entiendes HTTP/REST, no sabrás depurar cuando algo falle, ni diseñar tu API pública el día que la necesites, ni decidir bien entre las tres rutas. Aprende los fundamentos primero, los atajos después.

El patrón ganador en proyectos serios suele ser híbrido:

  • La lógica de acceso a datos vive en funciones reutilizables (lib/cars.js con getCarsByBrand(), createCar()...).
  • Los Server Components la usan directamente.
  • Los Route Handlers en /api/ la envuelven para exponerla a clientes externos.
  • Las Server Actions la envuelven para mutaciones desde Client Components.

Una sola lógica, tres formas de exponerla. Sin duplicación.

Diseña una API REST de gestión de pedidos para una pizzería online.

Recursos: pizzas, customers, orders. Una pizza puede aparecer en muchos pedidos. Un pedido lo hace exactamente un cliente. Un pedido tiene una o más pizzas.

Customer (1,1) ───  (0,N) Order
Order    (1,N) ───  (N,N) Pizza   // vía tabla intermedia

CREATE TABLE customers (

4 · Códigos de estado

  • 200 — GET listado, GET detalle, PATCH con respuesta.
  • 201 — POST con éxito (devolviendo el recurso creado).
  • 204 — DELETE con éxito.
  • 400 — JSON malformado o falta un campo obligatorio.
  • 401 — sin cookie session al pedir /api/orders.
  • 403 — usuario logueado pero pidiendo POST /pizzas sin ser admin.
  • 404 — GET /api/orders/9999.
  • 409 — POST /customers con email ya registrado.
