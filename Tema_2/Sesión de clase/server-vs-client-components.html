¿Dónde se ejecuta
tu componente?

En Next.js 13+, React puede ejecutarse en el servidor o en el navegador. Entender la diferencia lo cambia todo.

💡 Regla de oro En Next.js 13+, todos los componentes son Server por defecto. Solo añades 'use client' cuando necesitas interactividad. Piénsalo al revés: la pregunta no es "¿puede ser Server?" sino "¿tiene alguna razón para ser Client?"
Server Component — ejemplo real

No tiene 'use client' → es Server por defecto. Fíjate en el async/await directo:

app/productos/page.tsx
Server Component
// ✅ No necesita 'use client' — es Server por defecto

// async/await directamente en el componente 🤯
export default async function Productos() {

  // Esto corre en el SERVIDOR — el token nunca llega al browser
  const data = await fetch('https://api.ejemplo.com/productos', {
    headers: { Authorization: `Bearer ${process.env.API_SECRET}` }
  })
  const productos = await data.json()

  return (
    <ul>
      {productos.map(p => (
        <li key={p.id}>{p.nombre}</li>
      ))}
    </ul>
  )
}

// 👆 JS enviado al navegador: 0 bytes
Client Component — con 'use client'
components/Contador.tsx
Client Component
'use client'  // ← Esta directiva lo convierte en Client

import { useState } from 'react'

export default function Contador() {
  const [n, setN] = useState(0)  // ✅ hooks OK aquí

  return (
    <button onClick={() => setN(n + 1)}>
      Clicks: {n}
    </button>
  )
}

// 👆 Este JS SÍ se envía al navegador (hidratación)
La metáfora del restaurante
🍳 Server = La Cocina

El cliente nunca la ve. Allí se prepara todo, se accede a ingredientes privados (la base de datos), se usan herramientas caras (el servidor). Se entrega el plato ya hecho.

🍽️ Client = La Sala

El cliente la ve, interactúa con el camarero, puede pedir cambios (eventos). Necesita respuesta inmediata. No tiene acceso a los secretos de la cocina.

Composición

El árbol de
componentes

La regla más contraintuitiva de Next.js 13 y cómo mezclar Server y Client correctamente.

La regla más importante
✅ Server puede importar Client
// ProductPage.tsx (Server)
import ProductList from './ProductList'   ✓
import AddToCart from './AddToCart'     ✓
// AddToCart tiene 'use client' — OK

export default async function Page() {
  const data = await getProducts()
  return <ProductList products={data} />
}
❌ Client NO puede importar Server
'use client'

// ❌ ESTO FALLA
import ServerComp from './ServerComp'  ✗

export default function ClientComp() {
  return <ServerComp />  // ✗ Error!
}

// El Server Component se convierte
// en Client al ser importado así
⚠️ La solución: pasar como children (props) Un Client Component SÍ puede recibir un Server Component como children. El Server se renderiza en el servidor y se pasa como HTML al Client. Esta es la forma correcta de componer ambos tipos.
El patrón children — la solución correcta
// ✅ ClientWrapper.tsx — solo gestiona el click/estado
'use client'

export default function ClientWrapper({ children }) {
  return (
    <div onClick={() => console.log('clicked')}>
      {children}  // ← aquí puede vivir un Server Component
    </div>
  )
}

// ✅ Page.tsx (Server) — orquesta todo
import ClientWrapper from './ClientWrapper'
import ServerContent from './ServerContent'

export default async function Page() {
  return (
    <ClientWrapper>
      <ServerContent />  // ← Server como children ✅
    </ClientWrapper>
  )
}

next/font — fuentes sin layout shift
app/layout.tsx
Server Component
import { Inter, Roboto_Mono } from 'next/font/google'

// ✅ Se auto-hostea en tu servidor — sin petición a Google
const inter = Inter({
  subsets: ['latin'],
  display: 'swap',   // ← evita texto invisible durante carga
})

const mono = Roboto_Mono({
  subsets: ['latin'],
  variable: '--font-mono',  // ← CSS custom property
})

export default function RootLayout({ children }) {
  return (
    <html className={inter.className}>
      <body>{children}</body>
    </html>
  )
}

// 🏆 Resultado: 0 layout shift, 0 peticiones externas

Fase 2 · Reto — El patrón children
¿Cómo hacer que coexistan?

En el código de abajo, el componente FilterWrapper es Client (necesita estado para los filtros). Pero la lista de productos es Server (lee la BD). ¿Cómo los combinas sin romper las reglas?

Solución — patrón children
// 1️⃣ FilterWrapper.tsx — Client (necesita estado)
'use client'
import { useState } from 'react'

export function FilterWrapper({ children }) {
  const [cat, setCat] = useState('all')
  return (
    <div>
      <FilterButtons active={cat} onChange={setCat} />
      <div data-category={cat}>
        {children}  ← aquí van los productos (Server)
      </div>
    </div>
  )
}

// 2️⃣ page.tsx — Server (lee BD, async/await)
import { FilterWrapper } from './FilterWrapper'
import { ProductList } from './ProductList'

export default async function Page() {
  const products = await db.query('SELECT * FROM products')

  return (
    <FilterWrapper>
      <ProductList products={products} />  ← Server como children ✅
    </FilterWrapper>
  )
}
💡 Por qué funciona ProductList se renderiza en el servidor y Next.js pasa su HTML como children al FilterWrapper. El Client Component nunca "importa" el Server Component — solo recibe HTML ya renderizado. Esto permite mantener el máximo código en el servidor.
