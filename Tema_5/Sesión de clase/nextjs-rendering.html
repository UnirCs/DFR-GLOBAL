🚀 Next.js Rendering Playground

Explora interactivamente cómo funciona el renderizado en Next.js

📚 ¿Qué es el Renderizado?

El renderizado es el proceso de convertir el código JavaScript en HTML que el navegador pueda mostrar. En Next.js tienes varias opciones:

CSR

Client-Side Rendering

El navegador renderiza el contenido usando JavaScript.

👤 Renderizado en: Navegador

SSR

Server-Side Rendering

El servidor renderiza el HTML en cada solicitud.

🖥️ Renderizado en: Servidor

SSG

Static Site Generation

El HTML se genera una sola vez en tiempo de compilación.

⚡ Renderizado en: Build time

🎯 Objetivos de este playground:

  • Entender las diferencias entre CSR, SSR y SSG
  • Visualizar cómo funciona cada estrategia de renderizado
  • Aprender cómo configurar cada una en tu proyecto
  • Comparar ventajas y desventajas
  • Aprender a usar Loading.js para mejorar UX

🎨 Client-Side Rendering (CSR)

El navegador descarga un archivo JavaScript y lo ejecuta para renderizar el contenido dinámicamente.

Flujo de CSR

1️⃣ El navegador pide el HTML
GET /page → El servidor devuelve un HTML casi vacío (solo estructura)
2️⃣ Se descarga el JavaScript
El navegador descarga y parsea el bundle de JavaScript
3️⃣ Se ejecuta el JavaScript
El código JavaScript se ejecuta en el navegador y genera el HTML dinámicamente
4️⃣ Contenido visible
El usuario finalmente ve el contenido renderizado ✓

⚙️ Cómo configurar CSR en Next.js

  1. Usa 'use client' al inicio del archivo (Next.js 13+)
  2. Usa hooks de React: useState, useEffect, useContext
  3. Ideal para: Dashboards, aplicaciones interactivas, paneles de usuario
// app/posts/page.jsx
'use client'; // ← Renderizado en CLIENTE

import { useState, useEffect } from 'react';

export default function PostsPage() {
  const [posts, setPosts] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    // Se ejecuta SOLO en el navegador
    fetch('/api/posts')
      .then(res => res.json())
      .then(data => {
        setPosts(data);
        setLoading(false);
      });
  }, []);

  if (loading) {
    return <div>Cargando...</div>;
  }

  return (
    <div>
      {posts.map(post => (
        <article key={post.id}>
          <h2>{post.title}</h2>
        </article>
      ))}
    </div>
  );
}

🤔 ¿Por qué usar Client Components si los Server Components son más rápidos?

Los Server Components son más eficientes para renderizar contenido, pero hay casos donde los Client Components son imprescindibles o claramente superiores. No se trata de elegir uno u otro, sino de saber cuándo usar cada uno.

🖱️ Interactividad de usuario

Cualquier elemento que reaccione a acciones del usuario —clicks, inputs, drag & drop— requiere obligatoriamente un Client Component. Los Server Components se renderizan una sola vez en el servidor y no pueden escuchar eventos del DOM.

Ejemplos: formularios con validación en tiempo real, menús desplegables, modales, sliders.

🪝 Hooks de React

useState, useEffect, useRef, useContext, useReducer… solo funcionan en Client Components. Toda gestión de estado local o efectos secundarios del ciclo de vida de React exige el cliente.

Ejemplos: carrito de compra, filtros dinámicos, tema claro/oscuro.

🌐 APIs del navegador

window, localStorage, sessionStorage, navigator.geolocation, IntersectionObserver… estas APIs solo existen en el navegador. El servidor no tiene acceso a ellas.

Ejemplos: guardar preferencias, detectar ubicación, scroll infinito.

⚡ Actualizaciones en tiempo real

WebSockets, Server-Sent Events, polling periódico… todo flujo de datos en vivo necesita código que se ejecute continuamente en el cliente. Un Server Component solo puede devolver datos en el momento de la petición.

Ejemplos: chat en vivo, notificaciones push, precio de criptomonedas.

📦 Librerías de terceros

Muchas librerías populares (Framer Motion, React DnD, Recharts, Swiper, React Hook Form…) asumen que están en el navegador y fallarán si se ejecutan en el servidor. Requieren un Client Component como envoltorio.

Ejemplos: gráficas interactivas, animaciones, componentes UI avanzados.

🎯 UI optimista (Optimistic UI)

Actualizar la interfaz antes de que el servidor confirme la operación (como en Twitter al dar like) ofrece una experiencia instantánea. Esto requiere gestión de estado local en el cliente.

Ejemplos: likes, favoritos, reordenar listas con drag.

💡 La regla de oro:

Usa Server Components por defecto para todo lo que sea datos y estructura. Solo baja a Client Component cuando necesites interactividad. Cuanto más abajo en el árbol de componentes viva el 'use client', mejor rendimiento tendrás: el servidor sigue haciendo el trabajo pesado y el cliente solo gestiona la capa interactiva.

⚡ Server-Side Rendering (SSR)

El servidor renderiza el HTML completo en cada solicitud. El contenido es visible inmediatamente.

Flujo de SSR

1️⃣ El navegador pide el HTML
GET /page → El servidor recibe la solicitud
2️⃣ El servidor renderiza
El servidor ejecuta React y genera HTML completo
3️⃣ Se envía el HTML
El navegador recibe HTML renderizado y lo muestra
4️⃣ Hidratación
El JavaScript se descarga y hidrata el HTML (añade interactividad)

⚙️ Cómo configurar SSR en Next.js

  1. NO uses 'use client' - Por defecto es componente servidor
  2. Usa async/await directamente en el componente
  3. Usa fetch() directamente sin useEffect
  4. Ideal para: Blogs, tiendas, sitios dinámicos con SEO
// app/posts/page.jsx
// Sin 'use client' → SERVIDOR

async function PostsPage() {
  const res = await fetch(
    'https://api.example.com/posts',
    { next: { revalidate: 60 } }
  );
  const posts = await res.json();

  return (
    <div>
      {posts.map(post => (
        <article key={post.id}>
          <h2>{post.title}</h2>
        </article>
      ))}
    </div>
  );
}

export default PostsPage;

🎯 ¿Cuándo usar SSR? Casos de uso reales

SSR es la estrategia adecuada cuando el contenido cambia frecuentemente y necesita SEO, o cuando los datos deben ser personalizados por usuario en cada petición.

🛒 E-commerce y tiendas online

Las páginas de producto necesitan SEO (para que Google las indexe), pero el precio, el stock y las ofertas cambian constantemente. SSR garantiza que el usuario siempre ve datos actualizados sin sacrificar SEO.

Ejemplos: Amazon, Zara, páginas de detalle de producto.

📰 Portales de noticias

Las noticias se publican continuamente y deben aparecer en Google nada más publicarse. Con SSG habría que esperar al próximo build; con SSR el artículo es indexable desde el primer segundo.

Ejemplos: El País, BBC, portales de noticias en tiempo real.

👤 Páginas personalizadas por usuario

Contenido que varía según quién está autenticado: perfil de usuario, historial de pedidos, recomendaciones personalizadas. El servidor lee la sesión/cookie en cada petición y devuelve el HTML correcto para ese usuario concreto.

Ejemplos: perfil de LinkedIn, panel de cuenta en Amazon.

📊 Dashboards con datos críticos

Paneles donde los datos no pueden estar desactualizados ni un ciclo: cotizaciones bursátiles al inicio de la sesión, métricas de negocio en tiempo de petición, informes con cifras del momento exacto.

Ejemplos: paneles de analítica, reporting financiero.

🔍 Resultados de búsqueda

Las páginas de resultados de búsqueda dependen de parámetros de query (?q=zapatos) que son únicos por petición. No se pueden pre-generar estáticamente; hay que calcularlos en el momento de la solicitud.

Ejemplos: buscador de Airbnb, resultados de Google Shopping.

🌐 Contenido localizado (A/B, geo)

Mostrar precios en la moneda local, contenido adaptado al país o variantes de A/B testing. El servidor lee headers de la petición (Accept-Language, IP) y sirve el HTML adecuado sin redirecciones adicionales.

Ejemplos: Netflix por región, tiendas con precios en EUR/USD.

⚠️ Cuándo NO usar SSR:

Si el contenido no cambia entre peticiones (blog, documentación, landing page), usa SSG — es más rápido y barato. Si el contenido no necesita SEO pero sí mucha interactividad, usa CSR. SSR tiene un coste por petición en el servidor que solo vale la pena cuando los datos realmente varían.

⚙️ Static Site Generation (SSG)

El HTML se genera una sola vez durante el build. Súper rápido y escalable.

Flujo de SSG

1️⃣ Tiempo de BUILD
npm run build → Next.js pre-renderiza todas las páginas
2️⃣ Se guarda en el servidor/CDN
Los archivos HTML estáticos se almacenan
3️⃣ El navegador pide el HTML
GET /page → El servidor envía el HTML listo (instantáneo)
4️⃣ Hidratación
JavaScript se descarga y hidrata

⚙️ Cómo configurar SSG en Next.js

  1. NO uses 'use client' - Componente servidor
  2. Usa ISR: revalidate: 3600 (regenera cada hora)
  3. Para rutas dinámicas: Usa generateStaticParams()
  4. Ideal para: Blogs, docs, landing pages
// app/blog/page.jsx - Página estática

async function BlogPage() {
  const res = await fetch(
    'https://api.example.com/posts',
    { next: { revalidate: 3600 } }
  );
  const posts = await res.json();

  return (
    <div>
      {posts.map(post => (
        <div key={post.id}>
          <h2>{post.title}</h2>
        </div>
      ))}
    </div>
  );
}

export default BlogPage;
// Se pre-renderiza en BUILD
// app/blog/[slug]/page.jsx

async function PostPage({ params }) {
  const res = await fetch(
    `https://api.example.com/posts/${params.slug}`,
    { next: { revalidate: 3600 } }
  );
  const post = await res.json();

  return <article>{post.title}</article>;
}

// Define qué rutas generar en BUILD
export async function generateStaticParams() {
  const res = await fetch(
    'https://api.example.com/posts'
  );
  const posts = await res.json();

  return posts.map(post => ({
    slug: post.slug,
  }));
}

export default PostPage;

🏗️ La Estrategia Híbrida: Server + Client juntos

Next.js no te obliga a elegir entre Server o Client para toda la aplicación. La clave está en combinarlos dentro del mismo árbol de componentes: el servidor hace el trabajo pesado (datos, SEO, seguridad) y el cliente añade la capa interactiva donde es necesario.

// app/product/page.jsx — Server Component (por defecto)
async function ProductPage({ params }) {
// ✅ Fetch de datos en el servidor (seguro, rápido, sin JS en cliente)
const product = await getProduct(params.id);
return (
<div>
// Contenido estático: renderizado en servidor ⚡
<h1>{product.name}</h1>
<p>{product.description}</p>
// Interactividad: delegada al Client Component 🎯
<AddToCartButton productId={product.id} />
</div>
);
}

// components/AddToCartButton.jsx — Client Component
'use client'
function AddToCartButton({ productId }) {
const [added, setAdded] = useState(false);
return <button onClick={() => setAdded(true)}>{added ? '✅ Añadido' : '🛒 Añadir'}</button>;
}
Necesidad ¿Server o Client? Motivo
Fetch de datos de una API o DB 🖥️ Server Las credenciales no llegan al cliente y el fetch es más rápido
Botón con onClick / formulario 👤 Client Los eventos del DOM solo existen en el navegador
Contenido de blog / producto 🖥️ Server SEO, velocidad, sin JavaScript innecesario
Animaciones / transiciones UI 👤 Client Framer Motion y similares requieren acceso al DOM
localStorage / cookies del browser 👤 Client APIs exclusivas del navegador, no disponibles en servidor
Layout, nav, cabeceras estáticas 🖥️ Server No necesitan estado, no envían JS al cliente
Chat / datos en tiempo real 👤 Client WebSocket y polling requieren código que corra continuamente
🧠 Conclusión:

Los Client Components no compiten con los Server Components: los complementan. Next.js es rápido y óptimo precisamente porque permite usar Server Components para la estructura y datos, y Client Components solo donde la interactividad lo requiere. Sin Client Components, tendrías una web estática sin posibilidad de reaccionar al usuario.

📍 Loading.js: Mejorando UX

Loading.js muestra un estado de carga mientras se renderiza la página. Mejora la experiencia del usuario.

⚠️ Importante:

Next.js NO crea el skeleton automáticamente. Tienes que escribir toda la lógica y estilos manualmente. Next.js solo proporciona el archivo loading.jsx como punto de entrada para mostrar el estado de carga.

⚙️ Cómo configurar Loading.js

  1. Crea loading.jsx en el directorio de ruta
  2. Exporta un componente por defecto con tu diseño
  3. Escribe todo el código CSS/HTML - Next.js solo muestra el componente
  4. Se muestra automáticamente mientras carga el page.jsx

💡 Resumen: Skeleton vs Next.js

❌ Next.js NO proporciona:

  • Estilos CSS predefinidos para skeleton
  • Animaciones automáticas
  • Componentes skeleton pre-hechos

✅ Next.js SÍ proporciona:

  • El punto de entrada: archivo loading.jsx
  • La integración automática (muestra el componente mientras carga)
  • El flujo: loading → page transition

🎨 TÚ HACES: Todo el diseño, CSS, animaciones y estructura del loading

✨ Mejores Prácticas

  • ✅ Crea loading rápido: Debe aparecer en <100ms (sin lógica pesada)
  • ✅ Sé consistente: Mismo estilo en todas las páginas
  • ✅ Usa skeleton loaders: Imita el layout final del contenido
  • ✅ Añade feedback visual: Movimiento, colores, mensajes
  • ✅ No hagas cálculos: El loading debe ser puro JSX/CSS
