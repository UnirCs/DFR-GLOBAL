Antes de empezar

Estático y dinámico: cuándo, no cómo

Estos términos confunden mucho. No tienen nada que ver con si la página se mueve, tiene animaciones o es interactiva. Se refieren a cuándo se genera el HTML que llega al navegador.

▸ Estático
HTML pre-cocinado
El HTML se genera una vez, antes de que nadie lo pida. Todos los visitantes reciben el mismo archivo.
Ejemplos: Apple.com, blogs, docs, landing pages, fichas de producto. Pueden tener vídeos, animaciones, dark mode, formularios — siguen siendo estáticas.
▸ Dinámico
HTML al momento
El HTML se genera en cada visita. Cada usuario puede recibir un HTML distinto, según quién sea o qué pida.
Ejemplos: Tu bandeja de Gmail, tu carrito de Amazon, tu perfil de cualquier red social. Páginas que muestran datos personales o que cambian al instante.
◆ La confusión más común
Una página estática puede tener animaciones, vídeos, formularios, mapas interactivos y dark mode. Lo "estático" es solo el HTML inicial. Una vez en el navegador, JavaScript puede hacer lo que quiera. Renderizado e interactividad son cosas distintas.
◆ La pregunta clave

"¿El contenido cambia según quién pregunta?"

No → Estático
Inicio de un blog, ficha de producto en una tienda, página "sobre nosotros", landing.
Sí → Dinámico
Tu bandeja de entrada, tu carrito de compra, tu dashboard, tu perfil personal.
Categoría 01 · Estático

HTML pre-cocinado

El HTML se genera en el servidor antes de que nadie lo pida, se guarda como un archivo y se sirve desde un CDN. Es la categoría más rápida y barata. Incluye dos variantes: SSG (estático puro) e ISR (estático que se actualiza solo).

Static Site Generation

Cocina una vez, sirve mil veces

◆ Analogía
Como un libro impreso. Lo escribes una vez, lo imprimes, y cualquiera puede leerlo al instante. Pero si quieres cambiar algo, hay que reimprimir.
CDN
Content Delivery Network
Una red de copias de tu web repartidas por el mundo. Cuando alguien en Tokio pide tu página, la recibe desde un servidor en Tokio, no desde Madrid. Por eso las páginas estáticas son tan rápidas: no es que el servidor sea más potente, es que está más cerca.
Sin CDN: usuario en Tokio → servidor en Madrid → 10.000 km · ~300 ms
Con CDN: usuario en Tokio → copia en Tokio → 50 km · ~10 ms
Cloudflare, Vercel, Netlify y AWS CloudFront son CDNs. Si despliegas en Vercel o Netlify, tu CDN ya está montado.

◆ ¿Y si quiero actualizar el contenido?
PASO 1
Cambias el código o los datos
Editas un post, añades uno nuevo, cambias un texto en la API.
PASO 2
Subes a Git
Haces commit y push a GitHub, GitLab, etc.
git push
PASO 3
Build automático
Vercel (o Netlify, AWS...) detecta el push y ejecuta next build.
PASO 4
Sube al CDN
Los nuevos HTML se distribuyen y los visitantes ya ven la versión nueva.
En la práctica: con Vercel o Netlify, todo esto ocurre solo en 1-3 minutos tras un git push. Tú solo escribes y subes; el despliegue es automático. Si no usas un servicio así, tendrás que ejecutar next build y subir la carpeta .next a tu servidor manualmente.
Incremental Static Regeneration

Estático, pero se actualiza solo

Como SSG, pero la página se vuelve a generar cada X segundos. Rápido como un archivo, fresco como un servidor.

◆ Analogía
Como un periódico. Sale una edición, todos leen la misma. Cada cierto tiempo sale una nueva edición con los datos actualizados.

Categoría 02 · Dinámico

HTML al momento

El servidor genera la página cada vez que alguien la pide. Imprescindible cuando los datos dependen del usuario o cambian al instante. Aquí solo hay una variante: SSR.

app/dashboard/page.tsx SSR 
import { cookies } from 'next/headers'

export default async function Dashboard() {
  const session = cookies().get('session')
  // ↑ usar cookies() activa SSR automáticamente

  const user = await getUser(session.value)

  return <h1>Hola {user.name}</h1>
}
◆ Las 6 formas de activar SSR

Cualquiera de estas señales le dice a Next "esto no se puede pre-generar, hay que ejecutarlo en cada visita". La idea común: si tu código necesita algo que solo existe en el momento de la petición, Next pasa a SSR automáticamente.

cookies()
Leer cookies del usuario (sesión, preferencias).
headers()
Leer cabeceras HTTP (idioma, IP, user-agent).
searchParams
Leer parámetros de la URL (?page=2, ?q=zapatos).
fetch(url, { cache: 'no-store' })
Pedir datos sin cachearlos nunca.
export const dynamic = 'force-dynamic'
Forzar SSR explícitamente, sin necesidad de los anteriores.
export const revalidate = 0
Equivalente a "regenera siempre". Casi idéntico al anterior.
Úsalo cuando
  • Hay login y datos personales
  • Los datos cambian en tiempo real
  • Necesitas SEO con datos frescos
Evítalo cuando
  • El contenido es público y estable
  • Tienes mucho tráfico (es caro)
  • SSG o ISR ya valen
Categoría 03 · Cliente

HTML en el navegador

El servidor apenas trabaja: manda un HTML casi vacío y el navegador del usuario hace todo el trabajo de pintar la página con JavaScript. Aquí solo hay una variante: CSR.

app/feed/page.tsx CSR 
"use client"  // ← esta línea lo activa

import { useState, useEffect } from 'react'

export default function Feed() {
  const [posts, setPosts] = useState([])

  useEffect(() => {
    fetch('/api/feed').then(r => r.json()).then(setPosts)
  }, [])

  return <List items={posts}/>
}
◆ ¿Y el tiempo real? También funciona en CSR

Una confusión muy típica: pensar que CSR no sirve para datos en vivo. Falso. Lo que es lento en CSR es la carga inicial. Una vez la app está corriendo, el tiempo real funciona perfectamente — y de hecho es uno de sus puntos fuertes.

▸ WebSockets
Bidireccional
Conexión abierta entre navegador y servidor. El servidor empuja cambios al instante. Para chats, notificaciones, juegos multijugador, edición colaborativa.
▸ Polling
Pregunta cada N seg
El navegador pregunta al servidor "¿hay algo nuevo?" cada X segundos. Sencillo de montar. Para precios, stock, contadores, métricas.
▸ SWR / React Query
Refresco automático
Librerías que refrescan los datos solas cuando el usuario vuelve a la pestaña, recupera la conexión, o cada cierto tiempo. Lo más usado hoy.
Ejemplos reales: Discord, Notion, Figma, Linear o Google Docs son apps con mucho CSR y manejan tiempo real perfectamente. La diferencia con SSR no es "tiempo real sí o no", sino: SSR te da datos frescos al cargar la página, CSR te los da mientras usas la app. De hecho, lo más común es combinar SSR + CSR: SSR para la primera vista (rápida y con SEO), CSR después para la interactividad continua.
Úsalo cuando
  • La página está tras login
  • SEO no importa
  • App muy interactiva
Evítalo cuando
  • Necesitas indexarte en Google
  • Es contenido simple y estático
  • Usuarios con conexión lenta
Streaming + Suspense

Una capa, no un tipo

Streaming no es un renderizado distinto: es una técnica que se aplica encima de SSG, ISR o SSR. Hace que la página llegue en trozos en vez de toda de golpe.

◆ Importante · corrigiendo una confusión
SSG, ISR, SSR y CSR son tipos de renderizado (cuándo y dónde se genera el HTML). Suspense con streaming es una capa que combinas con los tres primeros para que la página no se bloquee esperando a la parte más lenta.
◆ Analogía
Como un restaurante que te trae el pan al sentarte, los entrantes a los 5 minutos y el plato fuerte después. No esperas con la mesa vacía. Da igual si el restaurante es de menú fijo (SSG), del día (ISR) o à la carte (SSR) — el servicio por trozos vale para cualquiera.

◆ Cómo se combina con cada tipo
▸ SSG + Suspense
Estático por trozos
Útil si una parte de tu página estática depende de datos que llegan más tarde durante el build. Poco común, pero válido.
▸ ISR + Suspense
Híbrido por trozos
Tu producto carga rápido (caché), pero las recomendaciones personalizadas pueden tardar. Suspense las muestra después sin bloquear.
▸ SSR + Suspense
El combo más útil
Dashboard con login (SSR) donde el header del usuario aparece ya y los widgets pesados van llegando. Lo verás constantemente.
app/dashboard/page.tsx SSR + streaming 
import { cookies } from 'next/headers'
import { Suspense } from 'react'

export default async function Dashboard() {
  const session = cookies().get('session')
  // ↑ esto activa SSR
  const user = await getUser(session.value)

  return (
    <>
      <h1>Hola {user.name}</h1>  {/* sale ya */}

      <Suspense fallback={<Skeleton/>}>
        <NotificacionesLentas />  {/* va llegando */}
      </Suspense>
    </>
  )
}
Combínalo cuando
  • Hay partes rápidas y partes lentas
  • Tienes SSR y quieres que algo aparezca ya
  • Una sección hace consultas pesadas
No hace falta cuando
  • Toda la página carga rápido por igual
  • Es CSR puro (ya tienes loading states)
  • Solo hay un bloque de contenido

¿Dónde se configura?

El ámbito: componente, página o proyecto

En Next.js no hay un panel de control. El tipo de renderizado se decide por el código que escribes, y el ámbito depende de dónde lo pongas.

▸ Más pequeño
Por componente
solo ese trozo
Marcas un único componente con "use client". El resto de la página sigue siendo del servidor. Útil para botones, formularios o widgets interactivos.
// Button.tsx "use client" export default function Button() { ... }
▸ Intermedio
Por página o ruta
esa URL completa
Lo más habitual. Pones la configuración en el page.tsx y solo afecta a esa ruta. Cada página de tu app puede tener un tipo distinto.
// app/blog/page.tsx export const revalidate = 60 export default function Page() {...}
▸ Más amplio
Por layout o segmento
esa rama de URLs
Si lo pones en un layout.tsx, afecta a todas las páginas debajo. Ej: todo /admin/* en SSR.
// app/admin/layout.tsx export const dynamic = 'force-dynamic' export default function Layout(){...}
◆ Idea clave
Una sola app puede mezclar los cinco tipos a la vez. Tu blog en SSG, la tienda en ISR, el dashboard en SSR, el editor en CSR — y todo en el mismo proyecto. Next.js elige el tipo página por página, no para toda la app.
Ejemplo real · una app de blog con tienda
  • / · landing → SSG
  • /blog/[slug] · posts → SSG
  • /tienda/[id] · productos → ISR
  • /cuenta · perfil → SSR
  • /admin · dashboard → CSR
Errores comunes que evitar
  • Poner "use client" en toda la app
  • Forzar SSR donde sirve SSG
  • Olvidar revalidate en datos cambiantes
  • Mezclar cookies() en página estática
